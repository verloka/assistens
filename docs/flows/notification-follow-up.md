# FDD-006 — Result delivery and conversational follow-up

Status: Draft

## Trigger / Outcome
- Initiator: task emits a notification-worthy result or authorized user asks a follow-up via an inbound channel.
- Outcome: result reaches permitted destination reliably, or follow-up continues relevant conversation and returns a new answer.

## Inputs
- Run result, notification destination/channel, delivery policy, conversation ID, inbound message and identity.

## Outputs
- Delivery record, message with result/source references, or a follow-up task/run referencing prior context.

## Flow
1. Convert run outcome to channel-neutral `OutgoingMessage` and persist to outbox.
2. Resolve only authorized destination(s); send with channel-specific adapter.
3. Retry temporary delivery failures while deduplicating message attempts as far as provider supports.
4. On incoming authorized natural-language follow-up, resolve conversation and load bounded prior context.
5. Submit new run through the common Task Runner and deliver outcome through the selected channel.

## Validations
- Authorized Telegram system commands are parsed before any model call: status/task queries and explicit-run pause/resume/cancel use common handlers and the expected run revision displayed by queries. Stale revision means no automatic retry; command identity is bound to the external update. Unknown slash commands and invalid arguments return bounded usage text without task submission. `/new <text>` and ordinary text submit through the common durable external-message path; no command or text grants tools, resolves approval tokens or trusts a supplied local conversation ID.
- Telegram long polling stores its next offset only after awaited durable acceptance (or explicit denial/unsupported transport discard). Restart/redelivery uses the same external update identity and common durable submission deduplication; a storage/callback failure cannot acknowledge later updates. Only bounded idempotent polling retries are allowed; no automatic webhook deletion, outbound write retry or credentials in diagnostics.
- Channel adapters pass bounded versioned neutral envelopes through common application commands. Bind transport channel/connection identity before authorization; sender/destination/text/attachments/action tokens remain untrusted data. Unknown routes or absent authorization deny by default. Plain tasks reuse durable per-route external-message identity and default local execution; channel data cannot select privileged tools/model policy or a local conversation ID. Outbound routing requires an exact authorized channel/connection/destination, makes no automatic retry and cannot alter task outcome. Unsupported action capabilities degrade to app-review text without exposing callback tokens.
- A peer binding is exact channel/connection/chat/sender to the current local owner. Unknown peers remain Pending until an explicit local owner revision-checked approval; repeated messages do not reactivate Revoked entries. Pending intake is bounded to100per owner/connection and stores identity metadata only, never bodies/tokens. Each new task/control/approval authorization checks current Approved binding; outgoing destinations require an Approved current-owner binding. A message or supplied decision Owner cannot create local authority. Revocation denies subsequent commands without rewriting already admitted task/approval outcomes.
- Sender/recipient allowlists, secrets/privacy policy, output size, channel-specific formatting and correlation IDs.
- Model-facing tools with dynamic recipients must bind trusted exact destination constraints to their validated arguments. A trusted fixed-route adapter retains its configured route; external content cannot choose a new outbound channel or obtain protected-store credentials.

## Invariants
- Communication channel does not contain task business logic.
- Failed delivery does not rewrite an otherwise completed TaskRun.
- Adding a second channel should require a new adapter/registration, not a Task Runner rewrite.

## Failures / Side Effects
- Network/Telegram errors are retried through outbox; no duplicate task execution due to notification failures.
- Unauthorized senders cannot use the bot to control desktop.

## Dependencies
- None.
